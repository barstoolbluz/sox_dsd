# SoX DSD CORE-MATH D6: Gain and Automatic Dither
## Independent engineering verdict — November 22, 2026

**Decision: ACCEPT. This is correct behavior, not a defect. Do not restore the old dither behavior.**

**Severity:** None  
**Disposition:** Approved; no corrective code change required.

### 1. Technical findings

The CORE-MATH implementation correctly calculates:

- `gain 20`: exactly 10.0
- `gain 40`: exactly 100.0

I independently compiled the supplied CORE-MATH `exp10.c` and verified both results.

The existing SoX gain implementation in `src/gain.c` preserves the input's effective precision when the gain multiplier is an integer. The automatic-dither logic in `src/sox_ng.c` adds dither when processing has increased effective precision beyond the output bit depth.

Neither mechanism is new. What changed is that the more accurate calculation now correctly identifies +20 dB and +40 dB as integer multipliers.

**This is the intended interaction between accurate gain calculation and SoX's established precision-tracking behavior.**

### 2. Independent reproduction

I tested the behavior using SoX 14.4.2 and a separate, deterministic 176,400-sample, 16-bit input.

At +20 dB:

| Measurement | Result |
|---|---|
| Original automatic-dither chain | input → gain → dither → output |
| Chain with automatic dither disabled | input → gain → output |
| Samples differing from exact 10× amplification with automatic dither | 43,875 / 176,400 |
| Maximum deviation | 1 LSB |
| Samples differing from exact 10× amplification without dither | 0 / 176,400 |

This independently reproduces the mechanism and closely matches the reported 44,061 differing samples. It is not a replay of the original project's exact test fixture, so that particular count remains unverified.

### 3. Why the new behavior is preferable

Dither is useful when quantization introduces an error that would otherwise correlate with the audio signal.

For a 16-bit integer input multiplied by exactly 10 or 100, every unclipped result is itself an exactly representable 16-bit integer.

There is no new quantization error requiring dither.

Adding dither in this situation introduces noise without correcting any quantization distortion.

The old gain calculation produced multipliers slightly different from their mathematical values. That caused SoX to classify the operation as requiring additional precision and consequently insert dither.

The new calculation removes that numerical approximation and its unnecessary downstream consequence.

**The new result is more mathematically faithful, retains the original samples' quantization structure, and introduces less noise.**

This reasoning assumes ordinary integer PCM input and no clipping. It does not suggest suppressing dither when preceding or subsequent processing genuinely increases effective precision.

### 4. Compatibility assessment

The change is externally observable: some 16-bit output samples differ by one least significant bit, and the automatic effect chain can change.

Nevertheless, this is not an unjustified behavioral regression.

- The documented purpose of CORE-MATH D6 is improved numerical fidelity.
- The governing D6 brief expressly permits nonzero-gain last-ULP changes and resulting signal-output differences.
- SoX's established automatic-dither policy remains unchanged.
- The changed output follows directly from correcting the gain multiplier.
- Neither the CLI syntax nor the documented automatic-dither contract promises identical output bytes across different numerical implementations.

Preserving the historical output would require deliberately adding unnecessary dither or reproducing the old numerical approximation.

Neither is technically justified.

If a particular workflow contractually requires byte-for-byte reproduction of files generated by an older version, that workflow should retain the older binary. It should not determine the mathematical behavior of the corrected implementation.

### 5. Recommended engineering action

**Do not change the gain calculation, effective-precision logic, or automatic-dither selection to restore the previous output.**

I recommend only modest maintenance:

1. Add a concise ChangeLog note explaining that correctly rounded integer gain factors can eliminate previously automatic dither.
2. Where the existing regression framework makes it straightforward, cover integer gain factors, noninteger gains, and explicit dither requests. Do not create a new testing framework for this.
3. Preserve the existing documented dither rules. No new CLI option, compatibility mode, or modification to `soxeffect_ng.7` is required solely because of this change.

The observed differences do not justify reopening the numerical implementation or modifying unrelated audio processing.

### Final determination

**APPROVED. No blocking defect.**

The CORE-MATH implementation has exposed an existing, intentional optimization in SoX: exact integer amplification can preserve the input bit depth without additional quantization noise.

The result differs from the old implementation because the new mathematics is more accurate, not because the DSP is malfunctioning.

**Accept the new output as authoritative. Do not sacrifice numerical correctness to reproduce unnecessary historical dither.**
