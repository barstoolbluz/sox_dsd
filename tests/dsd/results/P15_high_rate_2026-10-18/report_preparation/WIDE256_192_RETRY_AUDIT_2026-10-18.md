# DSD256 wideband → 192 kHz: two deadline retries

This is a read-only comparison of existing receipts and the actual frozen code. No numerical proof or hash-seed experiment was rerun. The [machine-readable audit](WIDE256_192_RETRY_AUDIT_2026-10-18.json) records exact receipt and supervision hashes, complete common identities, and all measurements.

## Observed results

| Canonical index and passband | Initial outcome | Initial proof wall / CPU, seconds | Retry outcome | Retry proof wall / CPU, seconds | Initial → retry CPU affinity |
|---|---|---:|---|---:|---:|
| 6673, 6–7 kHz | OPEN: interval wall-clock budget exhausted | 60.017 / 59.883 | PASS-LOCAL-BAND | 53.464 / 51.965 | 3 → 7 |
| 6678, 11–12 kHz | OPEN: interval wall-clock budget exhausted | 60.016 / 59.867 | PASS-LOCAL-BAND | 52.477 / 51.286 | 1 → 7 |

The initial signal/external limits were 60/85 seconds; the retries allowed 180/205 seconds. All four processes ended without external termination. Both successful proof calculations finished **before 60 seconds**, so these observations do not establish that a 180-second budget was necessary. Their peak RSS values were respectively 125,368→128,508 KiB and 125,352→125,380 KiB.

Within each pair, exact work, design digest, all 35 source pins, all 15 imported proof-module hashes, harness hash, stage snapshot, and verified operator binding are identical. The audit also checks the 15 modules against the current work and candidate3 files. The recorded Python executable/version, platform, mpmath/NumPy versions, `OPENBLAS_NUM_THREADS=1`, imported prover path and disabled profiling state agree. Only CPU affinity and permitted wall time differ in the recorded experiment identity; node/path limits stay at 128/20,000. These are therefore same-proof retries, with different resource settings, rather than matched timing measurements.

Both successful retries retain 9,408 complete paths and use seven proof nodes, three ordinary subdivisions, four proved children, one exact path enumeration and no exact routing split. Index 6673 uses 2,178 FIR evaluations, 1,351 finite-difference majorants and three terminal-saturation returns; index 6678 uses 2,174, 1,347 and three respectively. Their final alias uppers are 8.857247788022856×10⁻⁹ and 9.322055804797257×10⁻⁹.

## Traversal review

`make_native_stages` follows the manifest's stage-bank tuple; `make_src_stages` follows the captured operator stage sequence and sorts tap indices. In `complete_paths`, stages are traversed in reverse sequence, existing paths in list order, and branch integers in ascending `range(kmin, kmax+1)` order. Exact transition selection therefore follows the same deterministic sequence. The source-family set is used only for membership/count/minimum/maximum validation; its iteration order does not schedule work.

`bound_population` filters this ordered path sequence into a list. It inserts trie children in first-encounter order, and iterates Python dictionaries in that insertion order. Its `(id(stage), shift)` keys establish identity; object addresses are not used as ordering keys. Hash values affect dictionary lookup implementation, but do not change insertion order. The heap entry is `(priority, next(counter), ...)`: its explicit increasing counter resolves equal floating priorities before a node object could participate in comparison. Subtree-validation traversal is likewise driven by ordered children. Interval subdivision uses a list stack with a fixed append/pop order. Halfband and finite-difference preprocessing explicitly sort coefficients.

The 60/180-second allowance is passed to the deadline wrapper, not the certificate algorithm. It changes when an exception can interrupt calculation; it does not select a different bound, precision, path population or refinement policy. No hash-seed-dependent scheduling mechanism was found in these paths. This is a static argument about algorithmic order, not an empirical equality check of the two interrupted execution traces.

## What remains unknown

The harness catches a deadline exception and emits an OPEN receipt without partial FIR, trie or proof-node counters. Consequently the earlier attempts cannot be compared with the retry's traversal counts, and no exact instruction/work equivalence is claimed for the interrupted prefixes. The harness does not record `PYTHONHASHSEED`, hardware cycles/frequency, cache events, garbage-collection activity or a time series of concurrent load. Randomized hashes could affect runtime costs without changing dictionary traversal order; that possibility was not measured.

The initial attempts consumed almost their entire elapsed time as process CPU time, and that CPU time exceeds the complete retry CPU time. Simple waiting for scheduling time alone is therefore not an established explanation. The receipts show execution-time variability for the same identified proof and work on different CPU affinities. They do not identify its cause, demonstrate a hardware cause, establish an implementation speedup, or support a robust 60-second guarantee. The original OPEN receipts and successful retry certificates remain separate immutable observations.
